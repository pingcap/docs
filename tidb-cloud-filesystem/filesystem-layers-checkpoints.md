# TiDB Cloud Filesystem のレイヤーとチェックポイント

ファイルシステムのレイヤーは、共有されるベースデータとは分離したまま、ベースファイルシステム内のパスに対する変更を記録します。レイヤー内の変更は、そのレイヤーがコミットされたときにのみベースファイルシステムの一部になります。

レイヤーは checkpoint や fork も可能で、これによりレイヤー履歴内のある時点を保持したり、独立した子レイヤーで作業を継続したりできます。

ファイルシステムのレイヤーは Git ブランチとは独立しており、Git リポジトリも必要ありません。

レイヤーの作成、確認、fork、checkpoint、commit、rollback を行うコマンドについては、[ファイルシステムのレイヤーとチェックポイントを管理する](/tidb-cloud-filesystem/manage-filesystem-layers.md) を参照してください。

> **Note:**
>
> TiDB Cloud Filesystem は現在パブリックプレビューです。機能およびインターフェースは予告なく変更される場合があります。

## 基本概念 {#core-concepts}

- **Base file system:** レイヤーの外側にある共有ファイルシステムの状態です。レイヤーは、この状態をすぐには変更せずに、ベースパスに対する変更を記録します。
- **Layer:** ベースパスに対する書き込み可能な変更セットです。レイヤーがコミットされるまで、その変更はベースファイルシステムとは分離されたままです。
- **Checkpoint:** レイヤーの永続的な履歴内にある名前付きの時点です。checkpoint を作成すると、その時点がレイヤー履歴に保持されますが、レイヤーの変更はベースファイルシステムには適用されません。
- **Fork:** 別のレイヤーの現在の状態、またはその checkpoint の 1 つから作成される、新しい書き込み可能な子レイヤーです。fork 後に行われた変更は、親レイヤーと子レイヤーの間で独立します。
- **Commit:** レイヤー内の有効な変更をベースファイルシステムに適用します。
- **Rollback:** レイヤーの未コミットの変更を、ベースファイルシステムに適用せずに破棄します。rollback はレイヤーを以前の checkpoint に戻すものではありません。

## レイヤーとベースファイルシステム {#layers-and-the-base-file-system}

レイヤー内で行われた変更は、そのレイヤーを通しては見えますが、レイヤーがコミットされるまではベースファイルシステムには見えません。

レイヤーを指定しない操作は、ベースファイルシステムにアクセスします。つまり、未コミットのレイヤーがあっても、他のユーザーやアプリケーションがベースに直接アクセスしたときに見える内容は変わりません。

レイヤーは、ファイルシステム全体の完全なスナップショットではなく、ベースパス上に重ねられるオーバーレイです。fork や checkpoint は関連するレイヤー履歴を保持しますが、ベースファイルシステム全体を固定するわけではありません。そのため、引き続きベースから解決されるデータには、後から加えられたベース側の変更が反映されることがあります。

## fork と checkpoint {#forks-and-checkpoints}

checkpoint は、1 つのレイヤーの永続的な履歴内にあるある時点を保持します。別の書き込み可能レイヤーを作成するものではなく、変更をベースファイルシステムに公開することもありません。

checkpoint には読み取り専用のビューとしてアクセスできます。checkpoint から変更を続けるには、そこから新しい書き込み可能レイヤーを fork します。

fork は、fork が作成された時点での親レイヤーの履歴を保持します。その後、親レイヤーと子レイヤーでの新しい変更は互いに独立します。

checkpoint の作成時やマウントされたレイヤーの操作時における運用上の要件については、[ファイルシステムのレイヤーとチェックポイントを管理する](/tidb-cloud-filesystem/manage-filesystem-layers.md) を参照してください。

## commit と rollback {#commit-and-rollback}

レイヤーを commit すると、そのレイヤーの有効な変更がすべてベースファイルシステムに適用されます。これは Git commit ではなく、個々のファイルを選択的に公開するものでもありません。

commit は、レイヤーの親レイヤーではなく、ベースファイルシステムに変更を適用します。ベースファイルシステムに競合する変更が含まれている場合、変更が自動的にマージされるのではなく、commit が失敗することがあります。

レイヤーを rollback すると、変更を公開する代わりに未コミットの変更を破棄します。これはレイヤーを以前の checkpoint に戻すものではありません。

## 境界と制限事項 {#boundaries-and-limitations}

レイヤーは変更の分離を提供しますが、完全なファイルシステムスナップショット、バックアップ、または認可境界ではありません。ファイルシステムのパスや操作へのアクセスを制限するには、[scoped tokens](/tidb-cloud-filesystem/filesystem-authorization.md#scoped-tokens) を使用してください。

現在のレイヤーモデルには、次の制限があります。

- Git スタイルの merge および rebase 操作はサポートされていません。
- レイヤーをその場で checkpoint にリセットすることはできません。checkpoint から続行するには、新しいレイヤーを fork してください。
- 子レイヤーを commit しても、その変更は親レイヤーにはマージされません。
- レイヤーを削除すると論理的には破棄されますが、子孫レイヤーがその履歴に依存している間は、それらの子孫レイヤーから参照される履歴が引き続き利用可能な場合があります。
- レイヤーで作成されたファイルへの繰り返しの変更や継承されたメタデータを含む複雑な履歴では、パブリックプレビュー期間中に制限がある場合があります。

コマンド構文、フラグ、出力フィールドについては、[`ti fs` コマンドリファレンス](/ai/ti/reference/ti-filesystem.md) を参照してください。
