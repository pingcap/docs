# Log Redaction

When TiDB provides detailed log information, it might print sensitive data (for example, user data) in the log, which causes data security risks. To avoid such risks, each component provides a configuration item that redacts user data values. Starting from v8.5.9, log redaction is enabled by default. For an existing TiDB cluster, upgrading to v8.5.9 or a later version keeps the stored value of [`tidb_redact_log`](/system-variables.md#tidb_redact_log).

## Log redaction in TiDB side

Starting from v8.5.9, a new cluster sets [`tidb_redact_log`](/system-variables.md#tidb_redact_log) to `ON` by default, so user data in TiDB logs is replaced with `?`. For an existing cluster, the upgrade keeps the value already stored in the cluster. Before v8.5.9, the default value is `OFF`.

To enable log redaction, set `tidb_redact_log` to `ON` or `MARKER`. To disable log redaction, set it to `OFF`.

You can use the `set` syntax to set the global variable `tidb_redact_log`:

```sql
set @@global.tidb_redact_log = ON;
```

After the setting, all logs generated in new sessions are redacted:

```sql
create table t (a int, unique key (a));
Query OK, 0 rows affected (0.00 sec)

insert into t values (1),(1);
ERROR 1062 (23000): Duplicate entry '1' for key 't.a'
```

The error log for the `INSERT` statement above is printed as follows:

```
[2024/07/02 11:35:32.686 +08:00] [INFO] [conn.go:1146] ["command dispatched failed"] [conn=1482686470] [session_alias=] [connInfo="id:1482686470, addr:127.0.0.1:52258 status:10, collation:utf8mb4_0900_ai_ci, user:root"] [command=Query] [status="inTxn:0, autocommit:1"] [sql="insert into `t` values ( ... )"] [txn_mode=PESSIMISTIC] [timestamp=450859193514065921] [err="[kv:1062]Duplicate entry '?' for key 't.a'"]
```

From the preceding error log, you can see that when the value of `tidb_redact_log` is set to `ON`, sensitive information is replaced by the `?` mark in the TiDB log to avoid data security risks.

In addition, TiDB provides the `MARKER` option. When the value of `tidb_redact_log` is set to `MARKER`, TiDB marks sensitive information in the log with `‹›` instead of replacing it directly, so you can customize the redaction rules.

```sql
set @@global.tidb_redact_log = MARKER;
```

After the preceding configuration, the sensitive information is marked rather than replaced in all logs generated by new sessions:

```sql
create table t (a int, unique key (a));
Query OK, 0 rows affected (0.07 sec)

insert into t values (1),(1);
ERROR 1062 (23000): Duplicate entry '‹1›' for key 't.a'
```

The error log is as follows:

```
[2024/07/02 11:35:01.426 +08:00] [INFO] [conn.go:1146] ["command dispatched failed"] [conn=1482686470] [session_alias=] [connInfo="id:1482686470, addr:127.0.0.1:52258 status:10, collation:utf8mb4_0900_ai_ci, user:root"] [command=Query] [status="inTxn:0, autocommit:1"] [sql="insert into `t` values ( ‹1› ) , ( ‹1› )"] [txn_mode=PESSIMISTIC] [timestamp=450859185309483010] [err="[kv:1062]Duplicate entry '‹1›' for key 't.a'"]
```

As you can see from the preceding error log, after you set `tidb_redact_log` to `MARKER`, TiDB marks sensitive information using `‹ ›` in the log. You can customize redaction rules to handle sensitive information in the log as needed.

## Log redaction in TiKV side

Starting from v8.5.9, [`security.redact-info-log`](/tikv-configuration-file.md#redact-info-log-new-in-v408) defaults to `true`. If this item is omitted, TiKV redacts user data in logs, including after an upgrade. Set it to `false` or `"off"` to disable log redaction, or set it to `"marker"` to enclose sensitive values in `‹` and `›` while preserving their original values. Before v8.5.9, the default value is `false`.

## Log redaction in PD side

Starting from v8.5.9, [`security.redact-info-log`](/pd-configuration-file.md#redact-info-log-new-in-v50) defaults to `true`. If this item is omitted, PD redacts user data in logs, including after an upgrade. Set it to `false` to disable log redaction, or set it to `"marker"` to enclose sensitive values in `‹` and `›` while preserving their original values. Before v8.5.9, the default value is `false`.

The TSO and Scheduling services use the same default for [`security.redact-info-log`](/tso-configuration-file.md#redact-info-log) and [`security.redact-info-log`](/scheduling-configuration-file.md#redact-info-log).

## Log redaction in TiFlash side

Starting from v8.5.9, both the [`security.redact_info_log`](/tiflash/tiflash-configuration.md#configure-the-tiflashtoml-file) value in tiflash-server and the [`security.redact-info-log`](/tiflash/tiflash-configuration.md#configure-the-tiflash-learnertoml-file) value in tiflash-learner default to `true`. If either item is omitted, that component redacts user data in its logs, including after an upgrade. Set an item to `false` or `"off"` to disable log redaction for that component, or set it to `"marker"` to enclose sensitive values in `‹` and `›` while preserving their original values. Before v8.5.9, both default values are `false`.

## Log redaction in TiCDC

> **Note:**
>
> Starting from TiCDC v8.5.6, log redaction is supported only in the [TiCDC new architecture](/ticdc/ticdc-architecture.md).

Starting from v8.5.9, [`security.redact-info-log`](/ticdc/ticdc-server-config.md#redact-info-log-new-in-v856) defaults to `true` when it is not set. TiCDC then replaces sensitive values in logs with `?`. Set it to `false` to disable log redaction, or set it to `"marker"` to enclose sensitive values in `‹` and `›` while preserving their original values. Before v8.5.9, the default value is `false`.

## Log redaction in TiDB Lightning

Starting from v8.5.9, [`security.redact-info-log`](/tidb-lightning/tidb-lightning-configuration.md#redact-info-log) defaults to `true`. TiDB Lightning then replaces sensitive information in logs with `?`. Set it to `false`, or pass `--redact-info-log=false`, to disable log redaction. An explicit command-line value overrides the configuration file. Before v8.5.9, the default value is `false`.

## Log redaction in DM-worker side

Starting from v8.5.9, [`redact-info-log`](/dm/dm-worker-configuration-file.md#redact-info-log-new-in-v859-and-v900) defaults to `true`. DM-worker then replaces sensitive information in logs, including detailed query arguments, with `?`. Set it to `false`, or pass `--redact-info-log=false`, to disable log redaction. An explicit command-line value overrides the configuration file. This configuration item and flag are introduced in v8.5.9 and v9.0.0.

## Log redaction in sync-diff-inspector

Starting from v8.5.9, the top-level configuration item `redact-info-log` and the `--redact-info-log` flag default to `true`. sync-diff-inspector then replaces sensitive log fields with `?`, including SQL statements and their arguments, row values, chunk and histogram bounds, configuration dumps, column metadata, and comparison errors. Queries sent to the database, checkpoints, and generated fix SQL keep the original values. Set `redact-info-log` to `false`, or pass `--redact-info-log=false`, to disable log redaction. An explicit command-line value overrides the configuration file. If the configuration file has a syntax error, pass `--redact-info-log=false` on the command line to show the parsing error details. For more information, see [sync-diff-inspector User Guide](/sync-diff-inspector/sync-diff-inspector-overview.md#log-redaction-new-in-v859-and-v900).
